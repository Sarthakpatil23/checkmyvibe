## Scope

This is a **database-only check** (Check 4). Checks 1a/1b, 2, 3, 5, 6, and 7 are skipped and must be listed as skipped in the final summary.

## Step 1 — Run the first-pass script

```bash
python <skill_dir>/scripts/check_db_config.py <target>
```

It scans for:
- SQL migrations/schemas for tables created without RLS and permissive policies (`USING (true)` / `WITH CHECK (true)`) in BaaS stacks.
- Firestore/storage rules for `allow ...: if true` and Realtime Database rules set to `"true"`.
- Exposed SQLite database files (`.sqlite`, `.db`) located in web-accessible directories (`public/`, `static/`, `www/`, `dist/`).
- NoSQL/MongoDB direct object injection (`find(req.body)`).
- Insecure database connection configs (`sslmode=disable`, `rejectUnauthorized: false`).

If Python is unavailable or it fails, do the equivalent checks by reading schema/rules files manually and say so in the report.

## Step 2 — Determine the Database Architecture

Distinguish between two very different database models:

### Branch A: Client-Exposed BaaS (Supabase, Firebase, Convex)
In these stacks, the browser connects directly to the database using an anonymous public API key. Security MUST be enforced at the database row/collection level:

- **Supabase:** Every table holding user-specific data must have `ENABLE ROW LEVEL SECURITY`. A table without it → **Critical**.
- Policies granting broad access fail: `FOR SELECT USING (true)`, policies `TO public/anon` with unconditional USING/CHECK → **Critical**.
- Fix pattern:
  ```sql
  CREATE POLICY "users see own orders" ON orders
    FOR SELECT USING (auth.uid() = user_id);
  ```
- **Firebase:** `firestore.rules` containing `allow read, write: if true;` on user data collections → **Critical**. `database.rules.json` with `".read": "true"` → **Critical**.
- **Convex:** Ensure functions returning private data are defined as `internalQuery` or validate `ctx.auth.getUserIdentity()`.

### Branch B: Server-Backed Databases & ORMs (Neon, AWS RDS, Prisma, Drizzle, Local DBs, Mongo)
In these stacks, client browsers never talk to the database directly; all queries flow through a backend server (Express, FastAPI, Next.js server):

- **Do NOT flag missing RLS on server-only tables:** Standard SQL migrations generated by Prisma or Drizzle do not require Postgres RLS if queries are filtered in backend application code.
- **Neon & Serverless Pooling:** Verify that serverless functions connect via connection pooling (e.g. `@neondatabase/serverless` or PgBouncer pooled connection strings). Direct unpooled Postgres connections in serverless routes cause connection exhaustion and crashes → **Should Fix**.
- **SSL / Transport Security:** Database connection URIs or pool configs with `sslmode=disable` or `rejectUnauthorized: false` transmit credentials and data in cleartext → **Critical** in production.
- **SQLite / Embedded DBs:** SQLite databases (`*.db`, `*.sqlite`, `*.sqlite3`) placed in web-accessible public folders (`public/`, `static/`) or committed to git allow arbitrary database download by any visitor → **Critical**.
- **MongoDB / NoSQL Injection:** Passing unescaped `req.body` or `req.query` directly into Mongoose/MongoDB query filters (e.g., `User.findOne(req.body)`) allows query selector injection (`{ "$gt": "" }` bypassing passwords) → **Critical**.
- **Hardcoded DB Credentials:** Database connection strings with embedded plaintext passwords committed in code or schemas (e.g., in `schema.prisma` datasource) → **Critical**.

## Step 3 — Storage buckets

Supabase Storage, Firebase Storage, AWS S3:

- Public buckets holding private user content (documents, receipts, profile identity files) → **Critical**.
- Public buckets for genuinely public assets (avatars, static product images) → not findings; note the distinction.
